# Feature Specification: 프로젝트 생성·조회 (project)

**Feature Branch**: `project`

**Created**: 2026-11-16

**Status**: Draft

**Input**: User description: "팀장이 프로젝트를 만들고 조회하는 project 기능. 26-2 프로젝트 기획 4장·ERD 설계 기준. 범위: (1) 로그인한 사용자가 프로젝트 생성 — 입력: 이름, 소개(자유 텍스트), 기술 스택 태그(tag 기능의 TechStack), 예상 기간(개월 수, 1~36 정수), 회의 방식(OFFLINE/ONLINE), 목적(CONTEST/PORTFOLIO/STARTUP), 프로젝트 포지션 목록(tag 기능의 Position에서 골라 추가, 포지션마다 팀 정원). 생성하면 만든 사람이 팀장(ProjectMember role=LEADER, 포지션 없음)이 된다. 프로젝트 포지션 이름은 따로 저장하지 않고 마스터 Position 이름을 참조한다. (2) 프로젝트 상세 조회 (3) 내 프로젝트 목록 조회. 범위 밖: 공고(Recruitment)·지원·합류 제안, 프로젝트 정보 수정, 포지션 추가·삭제·정원 수정, 단체 채팅방(채팅 기능에서 워크스페이스에 붙임). 결정사항: 관리자가 마스터 Position을 삭제하면 그 Position을 가리키는 프로젝트 포지션도 함께 삭제되고(tag FR-007 계약대로), 그 프로젝트 포지션에 배정된 팀원·지원서는 '포지션 없음'(project_position_id null)으로 남는다. 기술 스택 태그 삭제 시 프로젝트-기술 스택 연결도 함께 삭제. 스키마 설계에서 정할 것(길이·개수 제한, 정원 범위, 중복 포지션 허용 여부, 응답 형태, 조회 권한 등)은 clarify에서 주인님과 대화로 채운다."

## Clarifications

### Session 2026-11-16 (specify 전 결정)

- Q: 기능 이름은? → A: `project`. 공고(Recruitment)는 별도 기능이다.
- Q: 이번 범위는? → A: 프로젝트 생성, 프로젝트 상세 조회, 내 프로젝트 목록 조회. 프로젝트 정보 수정과
  포지션 추가·삭제·정원 수정은 범위 밖이다.
- Q: 관리자가 마스터 포지션을 삭제하면 프로젝트 포지션은? → A: 그 포지션을 가리키는 프로젝트 포지션도 함께
  삭제된다(tag FR-007 계약). 그 프로젝트 포지션에 배정돼 있던 팀원(이후 지원서도)은 삭제되지 않고 "포지션 없음"
  상태로 남는다.
- Q: 단체 채팅방도 프로젝트 생성 때 만드나? → A: 아니오. 채팅 기능이 나중에 워크스페이스에 붙인다.
- Q: 팀장도 포지션을 갖나? → A: 생성 시점에는 포지션 없음으로 기록된다. 생성 요청에 팀장 포지션을 정하는
  항목은 없다. 이후 팀장 기능(포지션 배정)에서 팀장이 자기 자신에게도 포지션을 배정할 수 있다(범위 밖).

### Session 2026-11-16 (specify 표시 항목)

- Q: 같은 마스터 포지션을 한 프로젝트에 두 번 넣을 수 있나? → A: 아니오. 요청에 같은 포지션 id가 두 번 있으면
  400이고, 한 프로젝트 안에서 마스터 포지션은 고유하다.
- Q: 프로젝트 상세는 누가 조회하나? → A: 그 프로젝트의 현재 팀원(팀장 포함, 탈퇴·제외되지 않은 기록)만.
  비로그인은 401, 팀원이 아닌 로그인 사용자는 403이다. 공고 화면용 공개 정보는 공고 기능이 따로 정한다.
- Q: 내 프로젝트 목록 범위는? → A: 내 현재 팀원 기록(팀장 포함)이 있는 모든 프로젝트. 각 항목에 내 역할
  (`LEADER`/`MEMBER`)을 담는다. 이번 범위에서는 팀장 기록만 생기지만 합류 기능이 생기면 그대로 확장된다.

### Session 2026-11-16 (요구사항 체크리스트 `checklists/robustness.md`)

- Q: 입력 상한은? → A: 이름 1~50자, 소개 0~2000자, 기술 스택 0~20개, 포지션 0~10개, 포지션별 팀 정원 1~20명.
  포지션 없이(0개) 만들 수 있다. 길이는 앞뒤 공백 제거 후 문자 수로 센다.
- Q: 소개의 제어문자와 목록의 `null`은? → A: 소개는 줄바꿈·탭을 허용하고 그 밖의 제어문자는 400이다. 기술 스택·
  포지션 목록은 생략하거나 배열로만 보낼 수 있고 `null`이면 400이다.
- Q: 상세에 현재 팀원 목록을 담나? → A: 아니오. 팀원 목록은 합류·워크스페이스 기능이 따로 만든다.
- Q: 팀원이 아닌 사용자가 상세를 조회하면? → A: 403. 프로젝트 존재 여부는 숨기지 않는다.

### Session 2026-11-16 (팀장 포지션 변경)

- Q: 팀장 표시를 `is_leader` 같은 별도 값으로 바꾸나? → A: 아니오. 지금처럼 팀원 기록의 역할(팀장/팀원)로
  표시한다. 응답의 `myRole`, `leader: { id, nickname }`도 그대로다.
- Q: 팀장이 포지션을 가지면 그 포지션 정원에 들어가나? → A: 들어간다. 팀 정원은 팀장을 포함한 그 포지션의 총
  인원이다. 정원 계산은 공고·합류 기능의 일이다.
- Q: 팀장이 가진 포지션의 마스터 태그가 삭제되면? → A: 다른 팀원과 같이 팀장 기록도 남고 포지션만 없음이 된다.

### Session 2026-11-16 (워크스페이스 제외)

- Q: 프로젝트를 만들 때 워크스페이스도 만드나? → A: 아니오. 워크스페이스(모델·생성)는 이번 project 범위에서
  뺀다. 워크스페이스 기능이 나중에 프로젝트에 붙인다. 상세 응답에도 `workspaceId`가 없다.

### Session 2026-11-17 (포지션 이름 참조)

- Q: 프로젝트 포지션 이름을 생성 시 복사해 두나? → A: 아니오. 이름을 저장하지 않고 마스터 포지션 이름을 참조한다.
  관리자가 마스터 이름을 바꾸면 모든 프로젝트에 바로 반영된다.
- Q: 팀장이 자기 프로젝트에서만 포지션 이름을 바꿀 수 있나? → A: 아니오. 프로젝트 포지션은 정원만 바꿀 수
  있다(정원 수정은 범위 밖).
- Q: 응답에서 포지션은 어떤 모양인가? → A: `{ id, position: { id, name }, capacity }`. `positionId`·최상위
  `name`은 없다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 로그인한 사용자가 프로젝트를 만든다 (Priority: P1)

사용자는 함께할 사람을 모으기 전에 프로젝트를 먼저 만든다. 이름, 소개, 기술 스택, 예상 기간, 회의 방식, 목적을
정하고, 필요한 포지션을 관리자가 등록해 둔 포지션 목록에서 골라 포지션마다 팀 정원을 정한다. 만들면 그 사람이
팀장이 된다.

**Why this priority**: 공고·지원·합류·워크스페이스 기능 전부가 프로젝트를 전제로 한다. 프로젝트가 없으면
이후 흐름이 시작되지 않는다.

**Independent Test**: 기술 스택과 포지션 태그를 저장소에 미리 넣어 두고, 로그인한 사용자로 프로젝트를 만든 뒤
응답과 저장된 프로젝트·프로젝트 포지션·기술 스택 연결·팀장 팀원 기록을 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인한 상태이고 기술 스택 `"React"`, `"Node.js"`와 포지션 `"프론트엔드"`, `"백엔드"`가 있을 때,
   **When** 이름 `"MOP"`, 소개, 기술 스택 두 개, 예상 기간 `6`(개월), 회의 방식 `ONLINE`, 목적 `PORTFOLIO`, 포지션
   `"프론트엔드"` 정원 2·`"백엔드"` 정원 1로 프로젝트를 만들면, **Then** 201과 함께 새 프로젝트 상세(FR-008 형태)가
   반환되고, 프로젝트 1개, 프로젝트 포지션 2개(마스터 포지션 참조, 정원 2·1), 기술 스택 연결 2개, 만든 사람의
   팀장 팀원 기록 1개(포지션 없음)가 저장된다. 응답의 각 포지션 `position.name`은 마스터 포지션 이름이다.
2. **Given** 로그인한 상태, **When** 기술 스택과 포지션을 모두 생략(또는 빈 목록)하고 프로젝트를 만들면,
   **Then** 201이고 기술 스택 연결과 프로젝트 포지션은 0개이며 프로젝트와 팀장 기록은 저장된다.
3. **Given** 로그인한 상태, **When** 이름·소개·예상 기간·회의 방식·목적·기술 스택 목록·포지션 목록 중 하나라도 FR-003
   규칙을 어기면(예: 이름 51자, 소개 2001자, 예상 기간 0이나 37, 기술 스택 21개, 포지션 11개, 정원 0이나 21, 목록에 `null`),
   **Then** 400이 오고 프로젝트·프로젝트 포지션·연결·팀원 기록 중 아무것도 저장되지 않는다.
4. **Given** 로그인한 상태, **When** 존재하지 않는 기술 스택 id나 포지션 id가 하나라도 섞인 요청을 보내면,
   **Then** 400이 오고 아무것도 저장되지 않는다.
5. **Given** 로그인한 상태, **When** 같은 기술 스택 id를 두 번 보내면, **Then** 400이 오고 아무것도 저장되지
   않는다.
6. **Given** 로그인한 상태, **When** 같은 포지션 id를 두 번 보내면(정원이 같든 다르든), **Then** 400이 오고
   아무것도 저장되지 않는다.
7. **Given** 로그인하지 않은 상태, **When** 유효한 내용으로 프로젝트를 만들면, **Then** 401이 오고 아무것도
   저장되지 않는다.
8. **Given** 로그인한 상태이고 이미 다른 프로젝트의 팀장일 때, **When** 새 프로젝트를 만들면, **Then** 201이고
   두 프로젝트가 각각 팀장 기록을 갖는다(한 사람이 만들 수 있는 프로젝트 수 제한 없음).

### User Story 2 - 프로젝트 상세를 조회한다 (Priority: P2)

프로젝트의 팀원(팀장 포함)은 프로젝트 하나의 정보(이름, 소개, 기술 스택, 예상 기간, 회의 방식, 목적, 포지션과 팀 정원,
팀장)를 본다. 팀장은 만든 결과를 확인하고, 이후 프로젝트 대시보드·워크스페이스 화면이 이 정보를 보여 준다.
팀원이 아닌 사람은 볼 수 없다.

**Why this priority**: 생성(P1) 결과를 확인할 수단이자, 이후 프로젝트 대시보드·워크스페이스가 기대는 조회다.

**Independent Test**: 저장소에 프로젝트를 하나 만들어 두고 팀장으로 그 id의 상세를 조회해 응답 내용이 저장된 값과
같은지 확인한다. 다른 사용자·비로그인으로 같은 요청을 보내 403·401을 확인한다.

**Acceptance Scenarios**:

1. **Given** 프로젝트가 있을 때, **When** 그 프로젝트의 팀장으로 로그인해 상세를 조회하면, **Then** 200과 함께
   FR-008 형태의 상세가 반환된다.
2. **Given** 프로젝트 포지션이 여러 개, 기술 스택이 여러 개일 때, **When** 팀장이 상세를 조회하면, **Then** 포지션과
   기술 스택이 각각 FR-008의 정렬 규칙대로 온다.
3. **Given** 그 프로젝트에 현재 팀원 기록(역할 팀원)이 있는 사용자일 때, **When** 상세를 조회하면, **Then** 200과
   팀장이 보는 것과 같은 상세가 온다.
4. **Given** 그 프로젝트의 팀원이 아니거나 팀원 기록이 탈퇴·제외 처리된 사용자일 때, **When** 상세를 조회하면,
   **Then** 403이 온다.
5. **Given** 로그인하지 않은 상태, **When** 상세를 조회하면, **Then** 401이 온다.
6. **Given** 로그인한 상태이고 해당 id의 프로젝트가 없을 때, **When** 상세를 조회하면, **Then** 404가 온다.
7. **Given** 로그인한 상태, **When** id 형식이 올바르지 않은 값으로 조회하면, **Then** 400이 온다.
8. **Given** 팀장으로 로그인한 상태이고 포지션 `백엔드`가 있는 프로젝트가 있을 때, **When** 관리자가 그 마스터
   포지션 이름을 `서버`로 바꾼 뒤 팀장이 상세를 조회하면, **Then** 200과 함께 그 포지션의 `position.name`이
   `서버`로 오고 프로젝트 포지션 기록(id, project_id, position_id, capacity)은 바뀌지 않는다.

### User Story 3 - 내 프로젝트 목록을 조회한다 (Priority: P3)

로그인한 사용자는 자신이 현재 팀원(팀장 포함)으로 속한 프로젝트 목록을 보고 그중 하나로 들어간다. 각 항목에는
그 프로젝트에서의 내 역할이 함께 온다.

**Why this priority**: 여러 프로젝트를 만든(또는 참여하는) 사용자가 자기 프로젝트를 찾는 입구다. 생성(P1)과
상세(P2)에 의존한다.

**Independent Test**: 사용자 A·B가 각각 프로젝트를 만들어 둔 뒤 A로 목록을 조회해 A의 프로젝트만 오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 사용자 A가 프로젝트 두 개, 사용자 B가 프로젝트 하나를 만들었을 때, **When** A로 로그인해 내 프로젝트
   목록을 조회하면, **Then** 200과 `{ "items": [...] }` 형태로 A의 프로젝트 두 개만 최근 생성순으로 오고 각 항목의
   내 역할은 `LEADER`다.
2. **Given** 사용자 A가 B의 프로젝트에 현재 팀원 기록(역할 팀원)을 갖고 있을 때(저장소에 직접 준비), **When** A가
   목록을 조회하면, **Then** 그 프로젝트도 내 역할 `MEMBER`로 함께 온다. 팀원 기록이 탈퇴·제외 처리돼 있으면
   오지 않는다.
3. **Given** 로그인한 사용자가 속한 프로젝트가 없을 때, **When** 목록을 조회하면, **Then** 200과
   `{ "items": [] }`가 온다.
4. **Given** 로그인하지 않은 상태, **When** 목록을 조회하면, **Then** 401이 온다.

### User Story 4 - 관리자가 태그를 삭제해도 프로젝트는 남는다 (Priority: P4)

관리자가 기술 스택이나 포지션 태그를 삭제하면, 프로젝트는 그대로 남고 그 태그와의 연결만 사라진다. 삭제된
포지션을 쓰던 프로젝트 포지션은 함께 사라지고, 거기 배정돼 있던 팀원은 프로젝트에 남은 채 "포지션 없음"이 된다.

**Why this priority**: tag 기능의 삭제 계약(tag FR-007)을 프로젝트 쪽이 지키는지 확인한다. 생성(P1) 이후에만 의미가
있고 일상 흐름은 아니다.

**Independent Test**: 프로젝트를 만들고 그 프로젝트 포지션에 팀원 기록을 저장소에 직접 넣어 둔 뒤, 관리자로 해당
포지션 태그와 기술 스택 태그를 삭제하고 프로젝트·포지션·연결·팀원 기록 상태를 확인한다.

**Acceptance Scenarios**:

1. **Given** 기술 스택 `"React"`를 쓰는 프로젝트가 있을 때, **When** 관리자가 `"React"`를 삭제하면, **Then** 204이고
   프로젝트는 남으며 그 프로젝트의 `"React"` 연결만 사라진다. 이후 상세의 기술 스택 목록에 `"React"`가 없다.
2. **Given** 포지션 `"백엔드"`로 만든 프로젝트 포지션이 있고 그 프로젝트 포지션에 팀원 한 명이 배정돼 있을 때,
   **When** 관리자가 포지션 태그 `"백엔드"`를 삭제하면, **Then** 204이고 그 프로젝트 포지션은 삭제되며, 팀원 기록은
   남되 포지션이 없음으로 바뀐다. 팀장 기록과 다른 프로젝트 포지션은 그대로다.
3. **Given** 팀장 기록에 포지션 `"PM"`으로 만든 프로젝트 포지션이 배정돼 있을 때(저장소에 직접 준비), **When**
   관리자가 포지션 태그 `"PM"`을 삭제하면, **Then** 204이고 그 프로젝트 포지션은 삭제되며, 팀장 기록은 역할이
   팀장인 채로 남고 포지션만 없음으로 바뀐다. 상세의 `leader`와 목록의 `myRole`(`LEADER`)은 그대로다.
4. **Given** 포지션 `"백엔드"`를 쓰는 프로젝트 포지션이 그 프로젝트의 유일한 포지션일 때, **When** 관리자가
   `"백엔드"`를 삭제하면, **Then** 204이고 프로젝트는 포지션 0개로 남으며 상세 조회는 200에 빈 포지션 목록이다.

### Edge Cases

- 이름은 앞뒤 공백을 제거한 뒤 저장·길이 검증한다. 사이 공백은 그대로 둔다. 줄바꿈·탭 같은 제어문자는 400이다.
- 프로젝트 이름은 고유하지 않다. 같은 이름의 프로젝트가 여러 개 있어도 된다.
- 소개를 보내지 않거나 `null`·빈 문자열(공백만 포함)로 보내면 소개 없음(`null`)으로 저장한다. 소개 안의 줄바꿈·
  탭은 그대로 저장한다.
- 경계값: 이름 50자·소개 2000자·기술 스택 20개·포지션 10개·정원 1과 20·예상 기간 1과 36은 허용, 하나라도 넘으면 400이다.
- 예상 기간은 1~36 사이 정수(JSON 숫자)만 받는다. 0, 37, 소수, 숫자 문자열(`"6"`), 그 밖의 문자열은 400이다.
- 회의 방식·목적은 정해진 값만 받는다. 소문자(`"online"`)나 목록 밖 값은 400이다.
- 팀 정원은 정수만 받는다. 0, 음수, 소수, 문자열, 상한 초과는 400이다.
- 프로젝트 포지션 이름은 마스터 포지션 이름을 참조한다. 관리자가 마스터 포지션 이름을 바꾸면 이미 만든 프로젝트의
  상세·목록에도 바뀐 이름이 나온다.
- 생성은 하나의 단위로 처리한다. 중간에 실패하면 프로젝트·포지션·연결·팀원 기록 중 아무것도 남지 않는다.
- 생성 중 그 요청이 고른 태그가 동시에 삭제되면, 요청은 400(없는 태그) 또는 201(삭제 전 반영 후 FR-010대로 정리)
  중 하나로 끝나고 5xx는 나지 않는다.
- 탈퇴 처리된 사용자의 로그인 상태로 생성·상세·목록 요청을 하면 비로그인과 같은 401이다(auth FR-011).
- 다른 출처의 `Origin`을 붙인 생성 요청은 403이다(auth FR-013, 출처 검사가 가장 먼저). 상세·목록 조회는
  상태를 바꾸지 않으므로 출처 검사 대상이 아니다.
- 검사 순서(생성): 출처 검사(403) → 본문 JSON 파싱(400) → 로그인 확인(401) → 입력 형식 검증(400) → 태그 존재
  확인(400). 깨진 JSON은 비로그인이어도 400이다.
- 검사 순서(상세): 로그인 확인(401) → id 형식(400) → 프로젝트 존재(404) → 현재 팀원 여부(403).
- 포지션 태그 삭제로 포지션 없음이 된 팀원도 현재 팀원이므로 상세를 볼 수 있고 내 프로젝트 목록에 나온다.
- 정의되지 않은 추가 필드는 무시한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 로그인한 사용자는 프로젝트를 만들 수 있어야 한다. 성공 응답은 201이며 새 프로젝트의 상세(FR-008)를
  담는다. 비로그인 요청은 auth의 로그인 필수 보호와 같은 401이다.
- **FR-002**: 프로젝트 생성은 다음을 한 단위로 저장해야 한다: 프로젝트, 요청한 포지션마다 프로젝트 포지션(마스터
  포지션 참조 + 팀 정원), 요청한 기술 스택마다 연결, 만든 사람을 팀장 역할·포지션 없음으로 기록한 팀원
  기록 1개. 하나라도 실패하면 아무것도 저장하지 않는다.
- **FR-003**: 생성 입력 규칙. 위반 시 400이며 아무것도 저장하지 않는다.
  - 이름: 필수 문자열. 앞뒤 공백 제거 후 1자 이상 50자 이하(문자 수), 제어문자 금지.
  - 소개: 선택. 문자열 또는 `null`. 앞뒤 공백 제거 후 2000자 이하(문자 수). 줄바꿈·탭은 허용하고 그 밖의
    제어문자는 금지. 비었으면 `null`로 저장.
  - 예상 기간: 필수. 개월 수, 1 이상 36 이하 정수(JSON 숫자).
  - 회의 방식: 필수. `OFFLINE`, `ONLINE` 중 하나.
  - 목적: 필수. `CONTEST`(공모전), `PORTFOLIO`(포트폴리오), `STARTUP`(창업) 중 하나.
  - 기술 스택: 선택(생략 시 빈 목록, `null` 금지). 기술 스택 id(UUID) 배열, 0~20개, 중복 id 금지.
  - 포지션: 선택(생략 시 빈 목록, `null` 금지). `{ 포지션 id(UUID), 팀 정원 }` 배열, 0~10개. 팀 정원은 1 이상
    20 이하 정수. 같은 포지션 id가 두 번 있으면 400이다(정원이 달라도). 한 프로젝트 안에서 마스터 포지션은
    고유하다.
- **FR-004**: 요청한 기술 스택 id나 포지션 id 중 저장소에 없는 것이 하나라도 있으면 400이며 아무것도 저장하지
  않는다.
- **FR-005**: 한 사용자가 만들 수 있는 프로젝트 수에는 제한이 없다.
- **FR-006**: 프로젝트의 현재 팀원(팀장 포함, 탈퇴·제외되지 않은 팀원 기록이 있는 사용자)은 프로젝트 상세를 id로
  조회할 수 있어야 한다. 비로그인은 401, 팀원이 아닌 로그인 사용자는 403, 없는 프로젝트면 404, id 형식이 올바르지
  않으면 400이다.
- **FR-007**: 로그인한 사용자는 내 프로젝트 목록을 조회할 수 있어야 한다. 대상은 내 현재 팀원 기록(팀장 포함)이
  있는 모든 프로젝트다. 응답은 `{ "items": [...] }`이고 각 항목은 FR-008 상세에 내 역할 `myRole`(`LEADER` 또는
  `MEMBER`)을 더한 형태이며 프로젝트 생성 시각 내림차순이다. 비로그인은 401이다.
- **FR-008**: 프로젝트 상세 형태: `id`, `name`, `description`(없으면 `null`), `duration`(개월 수, 숫자), `meetingType`, `purpose`,
  `leader`(`{ id, nickname }`), `techStacks`(`[{ id, name }]`, 대소문자 무시 이름 오름차순), `positions`
  (`[{ id, position: { id, name }, capacity }]`, `id`는 프로젝트 포지션 식별자, `position`은 마스터 포지션(`id`,
  현재 `name`), `position.name` 기준 대소문자 무시 오름차순), `createdAt`, `updatedAt`. 팀장의 이메일·역할 등
  다른 사용자 정보는 담지 않는다. 현재 팀원 목록은 담지 않는다(합류·워크스페이스 기능의 범위).
- **FR-009**: 관리자가 기술 스택 태그를 삭제하면 그 태그와 프로젝트의 연결만 함께 삭제되고 프로젝트는 남는다(tag
  FR-007).
- **FR-010**: 관리자가 포지션 태그를 삭제하면 그 포지션을 가리키는 프로젝트 포지션도 함께 삭제된다(tag FR-007).
  그 프로젝트 포지션에 배정돼 있던 팀원 기록(팀장 기록 포함)은 삭제되지 않고 역할도 그대로이며 포지션만 없음으로
  바뀐다. 프로젝트, 그 포지션에 배정되지 않은 팀원 기록, 다른 프로젝트 포지션은 바뀌지 않는다.
- **FR-011**: 프로젝트 생성은 워크스페이스를 만들지 않는다. 워크스페이스는 워크스페이스 기능의 범위다.
- **FR-012**: 한 프로젝트에서 같은 사용자는 현재 팀원 기록(탈퇴·제외되지 않은 기록)을 하나만 가질 수 있고,
  팀장 역할의 기록은 프로젝트당 하나다.

### Key Entities *(include if feature involves data)*

- **Project(프로젝트)**: 팀장이 만든 협업 단위. 속성: 식별자(UUID), 팀장(사용자), 이름, 소개(선택), 예상 기간(개월 수),
  회의 방식, 목적, 생성·수정 시각, 삭제 시각(컬럼만 있고 아직 쓰지 않는다). 공고(별도 기능)는 프로젝트를 참조한다.
- **ProjectPosition(프로젝트 포지션)**: 프로젝트가 필요로 하는 역할. 속성: 식별자, 프로젝트, 마스터 포지션(tag의
  Position), 팀 정원(그 포지션의 총 팀원 수). 이름은 저장하지 않고 마스터 포지션에서 가져온다. 마스터 포지션이
  삭제되면 함께 삭제된다.
- **프로젝트-기술 스택 연결**: 프로젝트와 tag의 TechStack을 잇는다. 어느 쪽이 삭제되면 연결도 삭제된다.
- **ProjectMember(팀원 기록)**: 프로젝트에 속한 사람. 속성: 식별자, 프로젝트, 사용자, 프로젝트 포지션(선택; 팀장도
  가질 수 있고 생성 시 팀장은 없음, 포지션이 삭제되면 없음으로 바뀜), 역할(팀장/팀원, 프로젝트당 팀장 한 명),
  합류 시각, 탈퇴·제외 시각(선택). 포지션이 있는 팀원 기록은 역할과 관계없이 그 포지션의 팀 정원 한 자리를
  차지한다. 이번 범위에서 만드는 기록은 생성 시의 팀장 기록뿐이고, 포지션 배정은 이후 팀장 기능, 팀원 기록은
  이후 합류 기능이 만든다.
- **User / TechStack / Position**: auth·tag 기능에서 정의. 이 기능은 읽고 참조만 한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: US1~US4의 수용 시나리오 전부가 자동 테스트로 통과한다.
- **SC-002**: 생성이 실패한 모든 경우(입력 오류·없는 태그·비로그인)에 프로젝트·프로젝트 포지션·연결·팀원 기록이
  하나도 남지 않는다(테스트로 확인).
- **SC-003**: 잘못된 입력·없는 id는 모두 4xx로 응답하고 5xx가 발생하지 않는다.
- **SC-004**: 공고·합류·워크스페이스 기능 담당자가 이 기능의 파일을 수정하지 않고 프로젝트·프로젝트 포지션·팀원
  기록을 참조해 자기 기능을 만들 수 있다.

## Assumptions

- 로그인 필수 보호와 출처 검사는 auth 기능의 것을 그대로 쓴다: auth US3(로그인 필수 보호, FR-009·FR-011),
  auth US4(출처 검사, FR-013) 필요.
- 기술 스택·포지션 태그와 그 삭제 시 연결 삭제 계약은 tag 기능의 것을 쓴다: tag US2(목록), tag US4(삭제 시 연결
  함께 삭제, FR-007) 필요.
- 공고·지원·합류 제안·포지션 이동·팀원 탈퇴/제외, 프로젝트 정보 수정, 포지션 추가·삭제·정원 수정, 프로젝트 삭제,
  워크스페이스, 단체 채팅방, 일정·게시판은 범위 밖이다.
- 정원 계산(남은 자리)과 그 검사는 공고·합류 기능의 일이다. 이 기능은 팀 정원 값만 저장한다.
- 팀장이 탈퇴(소프트 딜리트)한 경우의 프로젝트 처리는 범위 밖이다. 상세는 저장된 팀장 정보를 그대로 보여 준다.
- 식별자는 사용자·태그와 같은 UUID 문자열이다.
- 목록의 페이지 나누기·검색·필터는 범위 밖이다. 한 사용자의 프로젝트는 수십 개 이하로 보고 전부 반환한다.
- 상세에 현재 팀원 목록을 담는 것은 범위 밖이다. 합류·워크스페이스 기능이 따로 만든다.
- 성능 목표는 범위 밖이다.
