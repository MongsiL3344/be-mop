# Feature Specification: 회원가입·로그인·세션 인증 (auth)

**Feature Branch**: `001-auth`

**Created**: 2026-11-02

**Status**: Draft

**Input**: User description: "유저 테이블·엔티티 만들고, 회원가입/로그인 만들고, 세션 인증 미들웨어를 넣어서 후배가 게시글 CRUD를 로그인 유저 기준으로 바로 시작할 수 있는 상태로 만든다. 로그인 식별자는 email + password + nickname."

## Clarifications

### Session 2026-11-02

- Q: 회원가입에 성공하면 그 자리에서 바로 로그인 상태가 되어야 하나? → A: 아니오. 가입은 201만
  반환하고 로그인은 별도로 한다.
- Q: 닉네임 길이 제한은? → A: 2자 이상 20자 이하.
- Q: 가입 성공 응답에 사용자 정보(id, email, nickname)를 담아야 하나? → A: 아니오. 201 빈 본문.
  사용자 정보는 로그인 응답에서만 반환한다.
- Q: 이메일 대소문자 처리는? → A: 가입·로그인 모두 검증 전에 앞뒤 공백 제거 후 전체 소문자로
  정규화해 저장·비교한다.
- Q: 사용자 삭제 방식은? → A: 소프트 딜리트. 삭제 시각(`deleted_at`)을 기록하고 행은 남긴다.
  탈퇴 API 자체는 이번 범위 밖이지만 데이터 모델과 조회 규칙은 처음부터 이를 전제로 한다.
- Q: 사용자 식별자 형식은? → A: UUID(문자열).
- Q: 탈퇴한 계정의 이메일·닉네임을 새 계정이 다시 쓸 수 있나? → A: 가능. 고유성은 탈퇴하지
  않은(활성) 계정 사이에서만 보장한다.
- Q: 비밀번호 규칙은? → A: 8자 이상이고 영문자와 숫자를 각각 1자 이상 포함해야 한다.

### Session 2026-11-03 (요구사항 체크리스트 `checklists/robustness.md`)

- Q: 같은 이메일·닉네임으로 동시에 가입하면? → A: 하나만 201, 나머지는 409. 어떤 경우에도 5xx가
  나지 않는다.
- Q: 로그인 요청 본문이 형식 오류(이메일 형식 아님, 필드 누락·타입 오류, JSON 아님)이면? → A: 400.
  401은 형식이 올바른 요청의 자격 증명 실패에만 쓴다.
- Q: 가입 409가 이메일 존재 여부를 드러내는 것은? → A: 허용한다. 409 응답은 이메일 중복인지 닉네임
  중복인지 구분해 알려준다. 계정 존재 비노출(FR-006)은 로그인에만 적용한다.
- Q: 입력 경계값은? → A: 비밀번호는 UTF-8 72바이트 초과 시 400. 닉네임 길이는 앞뒤 공백 제거 후
  기준이며 공백만 있으면 400. 이메일은 정규화 후 254자 초과 시 400.
- Q: 로그인 시도 제한·세션 재발급·성능 목표는? → A: 로그인 성공 시 로그인 상태 식별자를 새로
  발급한다(세션 고정 방지). 로그인 시도 제한과 성능 목표는 범위 밖.

### Session 2026-11-03 (요구사항 체크리스트 `checklists/login.md`)

- Q: 로그인 비밀번호가 가입 규칙에 어긋나면? → A: 빈 문자열과 UTF-8 72바이트 초과만 400(형식 오류).
  8자 미만·영문자/숫자 조합 위반은 자격 증명 실패로 보고 401. 정의되지 않은 추가 필드는 무시한다.
- Q: US2 독립 테스트에서 로그인 상태 인식을 무엇으로 판정하나? → A: 로그인 200 응답과 로그인 상태
  식별자 발급, 로그아웃 204와 식별자 폐기, 그리고 서버 세션 상태로 판정한다. 재로그인 시 이전 식별자
  폐기, 재로그인 실패 시 기존 상태 유지, 한 클라이언트 로그아웃이 다른 클라이언트에 영향 없음도 US2가
  서버 세션 상태로 검증한다.
- Q: 로그인한 상태에서 다시 로그인하다 실패(401·400)하면? → A: 기존 로그인 상태를 그대로 유지한다.
- Q: 같은 사용자가 여러 클라이언트에서 동시에 로그인하면? → A: 허용한다. 로그인 상태는 클라이언트별로
  독립이고 로그아웃은 그 클라이언트에만 적용된다.
- Q: 로그인 상태가 "서버 저장 데이터가 아니다"의 뜻은? → A: 데이터베이스 엔티티가 아니라는 뜻이다.
  로그인 상태는 기존 세션 미들웨어가 관리한다.

### Session 2026-11-04 (요구사항 체크리스트 `checklists/me.md`)

- Q: 후속 요청에서의 로그인 상태 인식은 어떻게 검증하나? → A: 로그인 상태 → 200, 로그아웃 후 → 401을
  US3 수용 시나리오로 검증한다. 재로그인·재로그인 실패·여러 클라이언트 로그아웃은 US2가 서버 세션
  상태로 이미 검증하므로 US3에서 반복하지 않는다.
- Q: "로그인 필수" 보호 수단은 통과한 요청에 무엇을 넘겨주고 어떻게 검증하나? → A: 로그인 사용자의
  id(UUID)를 제공한다. 내 정보 조회에 이 보호 수단을 적용해 검증한다.
- Q: 무엇을 비로그인으로 보나? → A: 식별자 없음·만료·위조·폐기, 탈퇴 계정 모두 401이며 같은 메시지로
  응답한다. 사용자 행은 하드 삭제하지 않으므로 "식별자가 가리키는 사용자 없음"은 다루지 않는다.
- Q: 탈퇴 계정의 로그인 상태가 감지되면? → A: 401로 거부한다. 그 로그인 상태를 폐기할지는 요구하지
  않는다.
- Q: socket.io 연결에도 로그인 필수 보호가 필요한가? → A: 범위 밖.

### Session 2026-11-04 (US4 출처 검사)

- Q: 보안 스캔에서 로그아웃이 다른 사이트의 폼 제출로 호출돼 로그인 쿠키가 지워질 수 있다고 나왔다.
  어떻게 막나? → A: 상태를 바꾸는 요청(GET·HEAD·OPTIONS 외 모든 메서드)의 `Origin` 헤더를 신뢰
  출처(프론트 주소, 기존 CORS 설정과 같은 값)와 비교해 다르면 403으로 거부한다. CSRF 토큰 방식은
  범위 밖.
- Q: `Origin` 헤더가 없는 요청은? → A: 허용한다. 브라우저는 다른 사이트에서 시작된 요청에 `Origin`을
  반드시 붙이므로, 헤더 없는 요청은 브라우저 밖(테스트 도구, curl)이거나 같은 출처로 본다. US1~US3
  테스트가 모두 `Origin` 없이 가입·로그인·로그아웃을 보내므로 이 정책은 그 테스트들이 검증하고 US4
  시나리오로 반복하지 않는다.
- Q: 검사 순서는? → A: 출처 검사는 본문 검증·로그인 확인보다 먼저다. 다른 출처의 요청은 본문이 어떻든
  403이며 세션·쿠키·DB를 바꾸지 않는다.

### Session 2026-11-06 (US5·US6 역할 구분, 요구사항 체크리스트 `checklists/role.md`)

- Q: 유저와 관리자는 어떻게 구분하나? → A: 사용자마다 역할 하나를 둔다. 값은 일반 사용자(USER)·관리자(ADMIN)
  두 가지이고 기본값은 일반 사용자다.
- Q: 관리자는 어떻게 지정하나? → A: 운영자가 저장소에서 역할 값을 직접 바꾼다. 역할 변경 API는 만들지 않는다.
- Q: 역할을 응답에 노출하나? → A: 로그인 응답과 내 정보 조회 응답에 role을 넣는다.
- Q: "관리자 전용" 보호 수단(로그인했지만 관리자가 아니면 403)도 여기서 만드나? → A: 아니오. 첫 사용처인 태그
  스펙(포지션·기술 스택 추가)에서 만들고 그 API로 검증한다. US5·US6은 역할 저장과 응답 노출까지만 다룬다.
- Q: 가입 본문에 role(예: `"ADMIN"`)이 실려 오면? → A: 무시하고 일반 사용자(USER)로 저장한다. 400으로
  거부하지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 회원가입 (Priority: P1)

방문자가 이메일, 비밀번호, 닉네임을 입력해 계정을 만든다. 만들어진 계정은 이후 로그인과
게시글 작성자 식별의 기준이 된다.

**Why this priority**: 계정이 있어야 로그인도, 게시글 작성자도 존재할 수 있다. 이 하나만 있어도
"사용자 데이터가 저장된다"는 가치가 생기고 게시글 기능의 외래키 대상이 확보된다.

**Independent Test**: 가입 요청 한 번으로 응답과 저장된 사용자 레코드를 확인하면 끝. 로그인 없이
단독 검증 가능.

**Acceptance Scenarios**:

1. **Given** 같은 이메일의 계정이 없을 때, **When** 유효한 이메일·비밀번호·닉네임으로 가입하면,
   **Then** 201 빈 본문으로 응답하고 사용자가 저장된다. 저장된 비밀번호는 원문이 아니어야 하며,
   가입 응답 후에도 로그인 상태는 시작되지 않는다.
2. **Given** 같은 이메일 또는 같은 닉네임의 계정이 이미 있을 때, **When** 그 이메일이나
   닉네임으로 가입하면, **Then** 409 충돌 응답이 오고 사용자 수는 늘지 않는다. 응답은 이메일
   중복인지 닉네임 중복인지 구분해 알려준다.
3. **Given** 어떤 상태든, **When** 이메일 형식이 아니거나 정규화 후 254자를 넘거나, 비밀번호가
   8자 미만이거나 UTF-8 72바이트를 넘거나 영문자·숫자 중 하나가 빠졌거나, 닉네임이 공백 제거 후
   2자 미만 또는 20자 초과이면, **Then** 400 응답이 오고 사용자는 저장되지 않는다.
4. **Given** 같은 이메일(또는 닉네임)의 활성 계정이 없을 때, **When** 그 값으로 가입 요청 여러 개가
   동시에 들어오면, **Then** 하나만 201로 저장되고 나머지는 409를 받으며 5xx는 나지 않는다.

---

### User Story 2 - 로그인 / 로그아웃 (Priority: P2)

가입한 사용자가 이메일과 비밀번호로 로그인하면 이후 요청에서 "누구인지"가 유지되고,
로그아웃하면 유지가 끝난다.

**Why this priority**: 게시글 작성·수정·삭제는 "로그인한 사용자" 기준이므로 로그인 상태 유지가
있어야 후배가 게시글 기능을 시작할 수 있다. 가입(P1)에 의존한다.

**Independent Test**: 가입된 사용자로 로그인 요청 → 200 응답과 로그인 상태 식별자 발급을 확인하고,
로그아웃 → 204 응답과 식별자 폐기를 확인. 재로그인·재로그인 실패·여러 클라이언트 로그아웃 뒤의 세션
상태도 여기서 확인한다. 실제 보호된 요청에서의 인식은 US3에서 검증한다.

**Acceptance Scenarios**:

1. **Given** 가입된 사용자, **When** 올바른 이메일·비밀번호로 로그인하면, **Then** 200과 함께
   사용자 정보(비밀번호 제외)가 반환되고 새로 발급된 식별자로 로그인 상태가 시작된다.
2. **Given** 가입된 사용자, **When** 비밀번호가 틀리거나(8자 미만·영문자/숫자 조합 위반 포함) 없는
   이메일로 로그인하면, **Then** 401 응답이 오고 로그인 상태는 시작되지 않는다. 이메일 없음과 비밀번호
   틀림은 같은 메시지로 응답한다(계정 존재 여부 노출 방지).
3. **Given** 로그인 상태, **When** 로그아웃하면, **Then** 204 응답이 오고 이후 요청은 로그인
   안 된 상태로 취급된다.
4. **Given** 어떤 상태든, **When** 로그인 요청 본문이 형식 오류(이메일 형식 아님, 필드 누락·타입
   오류, JSON 아님, 비밀번호가 빈 문자열이거나 UTF-8 72바이트 초과)이면, **Then** 400 응답이 오고
   로그인 상태는 시작되지 않는다. 정의되지 않은 추가 필드는 무시한다.

---

### User Story 3 - 내 정보 조회와 로그인 필수 보호 (Priority: P3)

로그인한 사용자는 자신이 누구인지 조회할 수 있고, 로그인이 필요한 기능은 로그인하지 않은
요청을 거부한다. 다른 기능(게시글 등)은 이 보호 수단을 그대로 가져다 쓴다.

**Why this priority**: 후배가 게시글 기능에 "로그인 필수"를 붙일 때 재사용할 공통 수단이다.
P1·P2가 있어야 검증 가능.

**Independent Test**: 로그인 전후로 내 정보 조회를 호출해 401 → 200으로 바뀌는지 확인.

**Acceptance Scenarios**:

1. **Given** 로그인 상태, **When** 내 정보를 조회하면, **Then** 200과 함께 로그인한 사용자의
   id, email, nickname, role이 반환된다.
2. **Given** 로그인하지 않은 상태(식별자 없음·만료·위조·폐기), **When** 내 정보를 조회하면, **Then**
   401 응답이 온다. 5xx는 나지 않는다.
3. **Given** 로그인 상태였으나 해당 사용자가 그 사이 탈퇴 처리(삭제 시각 기록)된 경우,
   **When** 내 정보를 조회하면, **Then** 시나리오 2와 같은 메시지의 401 응답이 온다.
4. **Given** 로그인 상태, **When** 로그아웃한 뒤 같은 클라이언트로 내 정보를 조회하면, **Then** 401
   응답이 온다.

---

### User Story 4 - 상태 변경 요청의 출처 검사 (Priority: P4)

다른 사이트에서 시작된 요청이 로그인 쿠키를 지우거나 사용자 데이터를 바꾸지 못하도록, 상태를
바꾸는 모든 요청의 출처를 확인한다. 게시글 등 이후 기능도 이 검사를 그대로 받는다.

**Why this priority**: 로그인 상태가 쿠키로 유지되므로 다른 사이트의 폼 제출이 그 쿠키에 영향을 줄 수
있다(강제 로그아웃). 계정 탈취는 아니지만 후속 기능(게시글 작성·삭제)이 생기기 전에 한 번에 막아야
한다.

**Independent Test**: 로그아웃 요청을 신뢰 출처·다른 출처 두 가지로 보내 각각 204·403을 확인하면 끝.
로그인된 클라이언트 하나면 충분하다.

**Acceptance Scenarios**:

1. **Given** 로그인 상태, **When** 신뢰 출처의 `Origin`을 붙여 로그아웃하면, **Then** 204가 오고
   로그인 상태가 끝난다(검사가 정상 요청을 막지 않는다).
2. **Given** 로그인 상태, **When** 다른 출처의 `Origin`을 붙여 로그아웃하면, **Then** 403이 오고 로그인
   쿠키를 지우는 응답이 없으며 그 클라이언트는 여전히 로그인 상태다.
3. **Given** 로그인 상태, **When** 다른 출처의 `Origin`을 붙여 내 정보를 조회(GET)하면, **Then** 검사
   대상이 아니므로 200이 온다.
4. **Given** 같은 이메일의 계정이 없을 때, **When** 다른 출처의 `Origin`을 붙여 유효한 값으로 가입하면,
   **Then** 403이 오고 사용자는 저장되지 않는다.

---

### User Story 5 - 가입하면 일반 사용자 역할을 받는다 (Priority: P5)

모든 계정은 일반 사용자(USER) 또는 관리자(ADMIN) 중 하나의 역할을 가진다. 새로 가입한 계정은 항상 일반
사용자이고, 가입 요청으로는 관리자가 될 수 없다. 관리자는 운영자가 저장소에서 역할 값을 직접 바꿔서 만든다.

**Why this priority**: 역할이 저장돼 있어야 응답 노출(US6)과 관리자 전용 기능(태그 추가 등)이 그 값을
기준으로 동작할 수 있다. 가입으로 관리자가 되는 길이 막혀 있어야 역할 구분이 의미를 가진다. 가입(US1)에
의존한다.

**Independent Test**: 가입 요청을 보낸 뒤 저장된 사용자의 역할이 일반 사용자인지 확인하면 끝. 로그인 없이
단독 검증 가능.

**Acceptance Scenarios**:

1. **Given** 같은 이메일의 계정이 없을 때, **When** 유효한 이메일·비밀번호·닉네임으로 가입하면, **Then**
   201 빈 본문으로 응답하고 저장된 사용자의 역할은 일반 사용자(USER)다.
2. **Given** 같은 이메일의 계정이 없을 때, **When** 유효한 가입 본문에 역할을 관리자(`"role": "ADMIN"`)로
   덧붙여 가입하면, **Then** 201이 오고 덧붙인 역할은 무시되어 저장된 역할은 일반 사용자(USER)다.

---

### User Story 6 - 로그인·내 정보 응답에 역할이 담긴다 (Priority: P6)

로그인한 사용자는 로그인 응답과 내 정보 조회 응답에서 자신의 역할을 받는다. 클라이언트는 이 값으로 관리자
화면 노출 여부를 정한다.

**Why this priority**: 클라이언트가 관리자 메뉴를 보여줄지 판단하려면 역할을 알아야 한다. 역할 저장(US5)과
로그인(US2)·내 정보 조회(US3)에 의존한다.

**Independent Test**: 일반 사용자와 관리자 계정을 각각 만들어 로그인·내 정보 조회 응답의 역할 값을 확인.

**Acceptance Scenarios**:

1. **Given** 일반 사용자 계정, **When** 올바른 자격 증명으로 로그인하면, **Then** 200과 함께 id, email,
   nickname, role(`"USER"`)이 반환된다.
2. **Given** 역할이 관리자로 저장된 계정, **When** 로그인하면, **Then** 200과 함께 role이 `"ADMIN"`으로
   반환된다.
3. **Given** 로그인 상태, **When** 내 정보를 조회하면, **Then** 200과 함께 id, email, nickname, 그리고 그
   시점에 저장된 role이 반환된다.
4. **Given** 일반 사용자로 로그인한 상태에서 그 계정의 역할이 저장소에서 관리자로 바뀌었을 때, **When**
   다시 로그인하지 않고 내 정보를 조회하면, **Then** role이 `"ADMIN"`으로 반환된다(조회 시점 값 기준).

---

### Edge Cases

- 이메일은 검증 전에 앞뒤 공백 제거 후 전체 소문자로 정규화한다. 따라서 `A@x.com`으로 가입한 뒤
  `a@x.com`으로 가입하면 409, `A@x.com`으로 로그인하면 성공한다. 저장된 값은 항상 소문자.
- 닉네임 앞뒤 공백은 저장 전에 제거하고, 길이 검증도 제거한 뒤 기준으로 한다. 공백만 있는 닉네임은
  400. 사이 공백(연속 공백 포함)은 그대로 저장하고 길이에 포함한다.
- 비밀번호 최대 길이는 문자 수가 아니라 UTF-8 72바이트다(한글·이모지가 섞이면 72자보다 짧아도 초과).
- 이미 로그인한 상태에서 다시 로그인하면 새 사용자로 로그인 상태가 교체되고, 이전 식별자는 폐기되어
  더 이상 로그인 상태로 인식되지 않는다(같은 사용자로 다시 로그인해도 같다).
- 로그인하지 않은 상태에서 로그아웃을 호출해도 204로 응답한다(멱등).
- 로그인한 상태에서 다시 로그인하다 실패(401·400)하면 기존 로그인 상태는 그대로 유지된다.
- 같은 사용자가 여러 클라이언트에서 동시에 로그인할 수 있다. 로그인 상태는 클라이언트별로 독립이고,
  한 클라이언트의 로그아웃은 다른 클라이언트에 영향을 주지 않는다.
- 탈퇴 처리된 계정으로 로그인을 시도하면 "없는 계정"과 동일하게 401(FR-006 단일 메시지).
- 탈퇴 처리된 계정의 기존 로그인 상태로 요청하면 비로그인과 같은 메시지의 401이다.
- 탈퇴한 계정과 같은 이메일로 새로 가입하면 201. 이후 그 이메일로 로그인하면 활성 계정으로만
  로그인된다.
- 요청 본문이 JSON이 아니거나 필드 타입이 다르면 400.
- 로그인 요청 본문이 형식 오류면 400(자격 증명 실패 401과 구분).
- 같은 값으로 동시에 가입하면 하나만 201, 나머지는 409(5xx 없음).
- `Origin` 비교는 스킴·호스트·포트까지 정확히 일치해야 한다. 끝 슬래시나 대소문자 차이는 다른 출처로
  본다.
- 다른 출처의 상태 변경 요청은 본문이 형식 오류여도 400이 아닌 403이다(출처 검사가 먼저).
- 다른 출처의 요청에 유효한 로그인 쿠키가 실려 있어도 403이며 세션은 그대로다.
- 가입 본문에 역할(`role`)을 어떤 값으로 넣어도(`"ADMIN"`, `"USER"`, 잘못된 값, 다른 타입) 무시하고 일반
  사용자로 저장한다. 역할 때문에 400이 나지 않는다. 다른 필드 검증 규칙은 그대로다.
- 로그인 응답의 역할은 로그인 시점에 저장된 값이다. 내 정보 조회의 역할은 조회 시점에 저장된 값이다(역할이
  올라가든 내려가든 같다).
- 탈퇴 처리된 관리자 계정도 다른 탈퇴 계정과 똑같이 존재하지 않는 계정으로 취급된다(로그인 401, 내 정보 401).
- 역할 구분 적용 전부터 있던 계정은 모두 일반 사용자 역할을 갖는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 이메일·비밀번호·닉네임으로 계정을 생성할 수 있어야 하며, 성공 응답은
  본문 없는 201이어야 한다.
- **FR-002**: 시스템은 이메일을 검증 전에 소문자로 정규화하고, 정규화된 이메일을 활성 계정
  사이에서 고유하게 보장해야 한다. 탈퇴한 계정의 이메일은 재사용 가능하다. 중복 가입 409 응답은
  이메일 중복임을 알려준다.
- **FR-003**: 시스템은 비밀번호를 복원 불가능한 형태로만 저장해야 하며 어떤 응답에도 비밀번호
  (원문·저장형 모두)를 포함하지 않아야 한다.
- **FR-004**: 시스템은 이메일 형식과 길이(정규화 후 254자 이하), 비밀번호(8자 이상, UTF-8 72바이트
  이하, 영문자 1자 이상과 숫자 1자 이상 포함), 닉네임(앞뒤 공백 제거 후 2자 이상 20자 이하)을 가입 시
  검증해야 한다.
- **FR-004a**: 가입 성공은 로그인 상태를 시작하지 않아야 한다. 로그인은 FR-005로만 시작된다.
- **FR-005**: 사용자는 이메일과 비밀번호로 로그인할 수 있어야 하며, 성공 시 후속 요청에서
  로그인 사용자가 식별되어야 한다. 로그인 성공 시 로그인 상태 식별자는 새로 발급해야 한다(세션 고정
  방지). 이미 로그인된 클라이언트가 다시 로그인하면 이전 식별자는 폐기되어 더 이상 인식되지 않아야 한다.
- **FR-006**: 로그인 실패 시 계정 존재 여부를 구분할 수 없는 단일 메시지로 401을 반환해야 한다.
  이 비노출 요구는 로그인에만 적용되며, 형식이 잘못된 로그인 요청(비밀번호가 빈 문자열이거나 UTF-8
  72바이트 초과인 경우 포함)은 400이다. 그 밖의 가입 비밀번호 규칙 위반은 자격 증명 실패(401)로 본다.
- **FR-007**: 사용자는 로그아웃할 수 있어야 하며 이후 그 클라이언트의 요청은 비로그인으로 취급되어야
  한다. 같은 사용자의 다른 클라이언트 로그인 상태에는 영향을 주지 않는다.
- **FR-008**: 로그인 사용자는 자신의 id, email, nickname과 조회 시점에 저장된 role을 조회할 수 있어야 한다.
- **FR-009**: 시스템은 "로그인 필수" 보호 수단을 제공해 다른 기능이 재사용할 수 있어야 하며,
  비로그인 요청은 401로 거부해야 한다. 비로그인은 식별자 없음·만료·위조·폐기, 탈퇴 계정을 모두
  포함하고 같은 메시지로 응답한다. 보호 수단을 통과한 요청에는 로그인 사용자의 id(UUID)가 제공된다.
  내 정보 조회(FR-008)는 이 보호 수단을 적용한다.
- **FR-010**: 시스템은 닉네임을 활성 계정 사이에서 고유하게 보장해야 하며 중복 닉네임 가입은
  409로 거부하고 닉네임 중복임을 알려야 한다. 탈퇴한 계정의 닉네임은 재사용 가능하다.
- **FR-011**: 사용자 삭제는 소프트 딜리트여야 한다. 삭제 시각이 기록된 계정은 로그인·내 정보
  조회·로그인 필수 보호 모두에서 존재하지 않는 계정으로 취급되어야 한다. 탈퇴 계정의 기존 로그인
  상태는 401로 거부한다.
- **FR-012**: 같은 이메일 또는 닉네임으로 가입 요청이 동시에 들어와도 활성 계정 간 고유성이
  지켜져야 한다. 하나만 성공(201)하고 나머지는 409이며 5xx를 내지 않는다.
- **FR-013**: 시스템은 GET·HEAD·OPTIONS를 제외한 모든 요청의 `Origin` 헤더를 신뢰 출처와 비교해
  다르면 403으로 거부해야 한다. `Origin`이 없으면 통과시킨다. 이 검사는 본문 검증·로그인 확인보다
  먼저 적용되고, 모든 기능의 라우트에 공통으로 적용된다.
- **FR-014**: 모든 사용자는 일반 사용자(USER)와 관리자(ADMIN) 중 정확히 하나의 역할을 가져야 한다.
  역할이 비어 있는 사용자는 없어야 한다.
- **FR-015**: 가입으로 만들어진 사용자의 역할은 항상 일반 사용자여야 한다. 가입 요청에 담긴 역할 값은
  무시한다.
- **FR-016**: 역할을 바꾸는 API는 제공하지 않는다. 관리자 지정은 운영자가 저장소에서 직접 한다.
- **FR-017**: 로그인 성공 응답은 id, email, nickname에 더해 role을 포함해야 한다. role 값은 `"USER"` 또는
  `"ADMIN"` 문자열이다(FR-008의 role도 같은 표기).
- **FR-018**: 역할 구분 적용 시점에 이미 있는 사용자는 모두 일반 사용자 역할을 가져야 한다.

### Key Entities *(include if feature involves data)*

- **User(사용자)**: 가입한 사람. 속성: 식별자(UUID), 이메일(활성 계정 간 고유, 소문자),
  비밀번호(저장형), 닉네임(활성 계정 간 고유), 역할(일반 사용자 USER 또는 관리자 ADMIN, 기본값 일반 사용자),
  가입 시각, 삭제 시각(없으면 활성). 이후 게시글(Post)의 작성자로 참조되고, 관리자 전용 기능(예: 포지션·기술
  스택 추가)이 역할을 기준으로 허용 여부를 판단한다.
- **로그인 상태(세션)**: 특정 클라이언트가 어떤 사용자로 로그인했는지 나타내는 상태.
  로그인으로 시작되고 로그아웃 또는 만료로 끝난다. 데이터베이스 엔티티가 아니며 기존 세션
  미들웨어가 관리한다. 같은 사용자도 클라이언트마다 독립된 로그인 상태를 가진다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 가입·로그인·로그아웃·내 정보 조회·출처 검사·역할 저장·역할 응답 노출 각각이 수용 시나리오
  전부를 자동 테스트로 통과한다.
- **SC-002**: 게시글 기능 담당자가 이 기능 머지 후 추가 인증 코드 없이 "로그인 필수" 보호를
  붙이고 로그인 사용자를 작성자로 사용할 수 있다(인증 관련 파일 수정 0건).
- **SC-003**: 어떤 응답 본문에도 비밀번호 원문이나 저장형이 포함되지 않는다(테스트로 확인).
- **SC-004**: 잘못된 입력(형식 오류·중복 이메일·잘못된 비밀번호)은 모두 4xx로 응답하고 5xx가
  발생하지 않는다.
- **SC-005**: 가입 요청만으로 관리자 역할을 얻는 경로가 0개다(테스트로 확인).

## Assumptions

- 인증 방식은 쿠키 기반 로그인 상태 유지(이미 프로젝트에 세션 미들웨어가 설정돼 있음).
  토큰 발급, 소셜 로그인, 비밀번호 재설정, 이메일 인증은 범위 밖이다.
- 비밀번호는 영문자·숫자 각 1자 이상 포함한 8자 이상이면 된다. 특수문자는 허용하되 요구하지
  않고, 최대 길이는 UTF-8 72바이트로 둔다(저장형 변환 방식의 입력 한계).
- 로그인 시도 횟수 제한과 성능 목표는 범위 밖이다.
- 로그인 상태 유지 기간은 기존 설정(7일)을 따른다.
- 회원 탈퇴 API, 프로필 수정은 범위 밖이다. 탈퇴는 데이터 모델(삭제 시각)만 준비한다.
- socket.io 연결의 로그인 필수 보호는 범위 밖이다. 보호 수단은 HTTP 요청에만 적용한다.
- 신뢰 출처는 프론트 주소 하나이며 기존 CORS 설정과 같은 값을 쓴다. 여러 출처 허용은 범위 밖이다.
- 세션 쿠키의 `SameSite=Lax`는 유지한다. 출처 검사는 그 위에 더하는 방어다. CSRF 토큰 방식은 범위
  밖이다.
- "활성 계정 간 고유"는 삭제 시각이 비어 있는 행에만 적용되는 부분 고유 제약으로 구현한다.
  스키마 도구가 이를 직접 표현하지 못하면 마이그레이션 SQL을 적용 전에 손봐야 한다.
- 이 기능은 팀장 브랜치에서 작업해 `dev`에 먼저 올라가고, 게시글 기능은 이를 기반으로 시작한다.
- 역할은 일반 사용자·관리자 두 가지뿐이다. 세분화된 권한, 여러 역할 동시 보유, 관리자 지정·해제 API,
  관리자 화면은 범위 밖이다. "관리자 전용" 보호 수단은 태그 스펙에서 만든다.
- 로그인·내 정보 응답 본문 전체를 비교하는 기존 US2·US3·US4 테스트 단언은 role이 추가된 응답에 맞게 고친다.
  응답 형태 변경 외의 기존 동작은 바꾸지 않는다.
- 역할 컬럼 추가는 아직 원격에 올라가지 않은 직전 마이그레이션(소개·링크 추가)과 하나로 합친다. 합칠 때
  개발·테스트 DB에 이미 적용된 직전 마이그레이션은 수동으로 되돌린다(전체 초기화 명령은 쓰지 않는다).
  개발 DB의 소개·링크 값은 사라진다.
