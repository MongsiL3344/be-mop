### Session 2026-11-07

- Q: 목록 조회는 누가 할 수 있나? → A: 로그인하지 않은 방문자를 포함해 누구나.
- Q: 사용자·공고와 태그를 잇는 연결도 이번 범위인가? → A: 아니오. 이번 범위는 기술 스택·포지션 두 종류와
  그 조회·추가·수정·삭제뿐이다. 연결은 사용자·공고 기능이 각자 만든다.

### Session 2026-11-07 (요구사항 체크리스트 `checklists/robustness.md`)

- Q: 나중에 사용자·공고가 연결한 태그를 삭제하면? → A: 연결도 함께 삭제된다. 태그 삭제는 연결 여부와 관계없이
  204로 성공하고, 그 태그를 가리키던 사용자·공고 연결만 사라진다. 연결을 만드는 기능은 이 규칙을 따라야 한다.
- Q: 이름 중복을 대소문자 구분해서 판단하나? → A: 구분하지 않는다. `"React"`가 있으면 `"react"` 추가는 409다.
  저장은 입력한 표기(앞뒤 공백 제거) 그대로 한다.
- Q: 이름 길이 단위와 허용 문자는? → A: 문자 수 기준 30자 이하. 특수문자·한글 등은 모두 허용하고 줄바꿈·탭 같은
  제어문자만 금지(400)한다.
- Q: 목록의 이름 오름차순은 대소문자·한글이 섞이면? → A: 대소문자를 무시한 알파벳순이다. 영문과 한글이 섞이면
  대소문자를 무시한 뒤 문자 코드 순서를 따른다(영문이 한글보다 앞).
- Q: 목록 응답 형태는? → A: 객체로 감싼다. `{ "items": [{ "id", "name" }, ...] }`.

### Session 2026-11-07 (본문 파싱 순서)

- Q: 본문이 JSON 문법부터 깨져 있으면 로그인·관리자 확인보다 먼저 400인가? → A: 그렇다. 본문 파싱은 앱 전체에
  공통으로 적용되며 출처 검사 바로 다음, 로그인·관리자 확인보다 먼저다. 따라서 깨진 JSON은 비로그인·일반 사용자
  요청이어도 400이다. JSON으로 읽히는 본문의 값 검증(이름 규칙 등)은 지금처럼 로그인·관리자 확인 뒤에 한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 관리자가 기술 스택·포지션을 추가한다 (Priority: P1)

관리자는 새 기술 스택(예: React)이나 포지션(예: 백엔드)을 이름으로 등록한다. 등록한 태그는 이후 사용자 프로필과
공고에서 고를 수 있는 선택지가 된다. 일반 사용자와 비로그인 방문자는 등록할 수 없다.

**Why this priority**: 태그가 하나도 없으면 조회·수정·삭제도, 사용자·공고 쪽 연결도 의미가 없다. "관리자 전용"
보호 수단도 여기서 처음 만들어지고 검증된다.

**Independent Test**: 관리자 계정으로 로그인해 기술 스택과 포지션을 하나씩 추가한 뒤 응답과 저장된 행을 확인한다.
같은 요청을 일반 사용자·비로그인으로 보내 403·401과 저장 안 됨을 확인한다.

**Acceptance Scenarios**:

1. **Given** 관리자로 로그인한 상태이고 같은 이름의 기술 스택이 없을 때, **When** 기술 스택 이름 `"React"`로
   추가하면, **Then** 201과 함께 새 태그의 id와 name이 반환되고 기술 스택이 1개 저장된다.
2. **Given** 관리자로 로그인한 상태이고 같은 이름의 포지션이 없을 때, **When** 포지션 이름 `"백엔드"`로 추가하면,
   **Then** 201과 함께 id와 name이 반환되고 포지션이 1개 저장된다.
3. **Given** 관리자로 로그인한 상태이고 `"React"` 기술 스택이 이미 있을 때, **When** `"React"` 또는 대소문자만 다른
   `"react"`로 다시 추가하면, **Then** 409가 오고 기술 스택 수는 늘지 않는다.
4. **Given** 관리자로 로그인한 상태, **When** 이름이 없거나, 문자열이 아니거나, 앞뒤 공백 제거 후 비었거나 30자를
   넘거나, 줄바꿈·탭 같은 제어문자를 포함하면, **Then** 400이 오고 아무것도 저장되지 않는다.
5. **Given** 일반 사용자(USER)로 로그인한 상태, **When** 유효한 이름으로 기술 스택이나 포지션을 추가하면,
   **Then** 403이 오고 아무것도 저장되지 않는다.
6. **Given** 로그인하지 않은 상태, **When** 유효한 이름으로 기술 스택이나 포지션을 추가하면, **Then** 401이 오고
   아무것도 저장되지 않는다.
7. **Given** 관리자로 로그인한 상태이고 같은 이름의 기술 스택이 없을 때, **When** 같은 이름의 추가 요청 여러 개가
   동시에 들어오면, **Then** 하나만 201로 저장되고 나머지는 409를 받으며 5xx는 나지 않는다.

### User Story 2 - 누구나 기술 스택·포지션 목록을 조회한다 (Priority: P2)

방문자와 사용자는 프로필 작성, 공고 작성, 공고 검색 필터에서 고를 수 있도록 기술 스택 목록과 포지션 목록을
조회한다. 로그인하지 않아도 된다.

**Why this priority**: 등록된 태그를 클라이언트가 보여줘야 사용자·공고 기능이 태그를 고르게 할 수 있다.
추가(P1) 다음으로 필요하다.

**Independent Test**: 저장소에 기술 스택과 포지션을 몇 개 직접 넣어 두고, 로그인 없이 각 목록을 조회해 전체가
대소문자를 무시한 이름순으로 오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 기술 스택 `"TypeScript"`, `"jQuery"`, `"React"`, `"angular"`가 저장돼 있을 때, **When** 로그인하지 않고
   기술 스택 목록을 조회하면, **Then** 200과 함께 `{ "items": [...] }` 형태로 네 개 모두 id와 name을 담아
   `"angular"`, `"jQuery"`, `"React"`, `"TypeScript"` 순서(대소문자 무시 오름차순)로 반환된다.
2. **Given** 포지션 `"프론트엔드"`, `"백엔드"`, `"DevOps"`가 저장돼 있을 때, **When** 로그인하지 않고 포지션 목록을
   조회하면, **Then** 200과 함께 `"DevOps"`, `"백엔드"`, `"프론트엔드"` 순서로 반환되고 기술 스택은 섞이지 않는다.
3. **Given** 저장된 기술 스택이 없을 때, **When** 기술 스택 목록을 조회하면, **Then** 200과 `{ "items": [] }`가
   반환된다.
4. **Given** 일반 사용자로 로그인한 상태, **When** 목록을 조회하면, **Then** 비로그인과 같은 결과가 200으로 온다.

### User Story 3 - 관리자가 기술 스택·포지션 이름을 수정한다 (Priority: P3)

관리자는 오타가 있거나 표기를 통일해야 하는 태그의 이름을 바꾼다. 태그의 식별자는 그대로라서 나중에 이 태그를
가리키는 연결도 그대로 유지된다.

**Why this priority**: 잘못 등록한 태그를 지우고 다시 만들지 않고 고칠 수 있어야 한다. 추가(P1)에 의존한다.

**Independent Test**: 관리자로 태그 하나를 만들어 두고 이름을 바꾼 뒤 응답과 저장된 이름을 확인한다. 일반 사용자로
같은 요청을 보내 403과 이름 그대로임을 확인한다.

**Acceptance Scenarios**:

1. **Given** 관리자로 로그인한 상태이고 기술 스택 `"Recat"`이 있을 때, **When** 그 이름을 `"React"`로 수정하면,
   **Then** 200과 함께 같은 id와 새 이름이 반환되고 저장된 이름이 바뀐다.
2. **Given** 관리자로 로그인한 상태이고 포지션 `"백엔드"`, `"DevOps"`가 있을 때, **When** `"백엔드"`의 이름을
   `"devops"`(대소문자만 다른 기존 이름)로 수정하면, **Then** 409가 오고 두 포지션 이름은 그대로다.
3. **Given** 관리자로 로그인한 상태, **When** 존재하지 않는 id의 기술 스택이나 포지션을 수정하면, **Then** 404가
   온다.
4. **Given** 관리자로 로그인한 상태, **When** 이름이 FR-005 규칙을 어기거나 id 형식이 올바르지 않으면, **Then**
   400이 오고 저장된 이름은 그대로다.
5. **Given** 일반 사용자로 로그인한 상태, **When** 태그 이름을 수정하면, **Then** 403이 오고 이름은 그대로다.
6. **Given** 로그인하지 않은 상태, **When** 태그 이름을 수정하면, **Then** 401이 오고 이름은 그대로다.

### User Story 4 - 관리자가 기술 스택·포지션을 삭제한다 (Priority: P4)

관리자는 더 쓰지 않는 태그를 목록에서 없앤다. 일반 사용자와 비로그인 방문자는 삭제할 수 없다.

**Why this priority**: 목록 정리는 필요하지만 추가·조회·수정보다 덜 급하다. 추가(P1)에 의존한다.

**Independent Test**: 관리자로 태그 하나를 만들어 두고 삭제한 뒤 204와 저장소에서 사라졌음을 확인한다. 일반
사용자로 같은 요청을 보내 403과 그대로 남아 있음을 확인한다.

**Acceptance Scenarios**:

1. **Given** 관리자로 로그인한 상태이고 기술 스택 `"jQuery"`가 있을 때, **When** 그 기술 스택을 삭제하면,
   **Then** 204 빈 본문이 오고 저장소에서 사라지며 이후 목록에도 나오지 않는다. 연결된 사용자·공고가 있어도
   같은 결과다(연결도 함께 사라짐, FR-007). 연결 기능이 아직 없으므로 이 부분은 연결 기능 쪽 테스트가 검증한다.
2. **Given** 관리자로 로그인한 상태이고 포지션 `"퍼블리셔"`가 있을 때, **When** 그 포지션을 삭제하면, **Then**
   204가 오고 저장소에서 사라진다. 같은 이름의 포지션을 다시 추가하면 201이다.
3. **Given** 관리자로 로그인한 상태, **When** 존재하지 않는(또는 이미 삭제된) id를 삭제하면, **Then** 404가 온다.
4. **Given** 관리자로 로그인한 상태, **When** id 형식이 올바르지 않은 값으로 삭제하면, **Then** 400이 온다.
5. **Given** 일반 사용자로 로그인한 상태, **When** 태그를 삭제하면, **Then** 403이 오고 태그는 그대로 남는다.
6. **Given** 로그인하지 않은 상태, **When** 태그를 삭제하면, **Then** 401이 오고 태그는 그대로 남는다.

---

### Edge Cases

- 이름은 앞뒤 공백을 제거한 뒤 저장·비교·길이 검증한다. `"  React "`로 추가하면 `"React"`로 저장되고, 이미
  `"React"`가 있으면 409다. 사이 공백은 그대로 둔다.
- 이름 중복은 대소문자를 무시하고 판단한다(`"React"`가 있으면 `"react"`·`"REACT"`는 409). 저장은 입력한 표기 그대로다.
- 길이는 문자 수로 센다. 한글 30자는 허용, 31자는 400이다. 특수문자(`"C++"`, `"C#"`, `"Node.js"`)와 사이 공백은
  허용하고, 줄바꿈·탭 등 제어문자가 하나라도 있으면 400이다(앞뒤 공백 제거 후에도 남는 경우).
- 기술 스택과 포지션은 서로 다른 목록이다. 같은 이름(예: `"DevOps"`)이 기술 스택과 포지션에 각각 있어도 된다.
- 수정 시 자기 자신의 현재 이름과 같은 이름(대소문자만 다른 표기 포함, 예: `"react"` → `"React"`)으로 바꾸면
  중복이 아니며 200이고 새 표기로 저장된다.
- 수정 중 다른 태그와 같은 이름으로 동시에 바뀌는 경우에도 같은 목록 안 이름 고유성이 지켜지고 5xx가 나지 않는다.
- 검사 순서: 출처 검사(403) → 본문 JSON 파싱(400) → 로그인 확인(401) → 관리자 확인(403) → 입력 값 검증(400) →
  존재·중복 확인(404·409). 깨진 JSON은 비로그인·일반 사용자 요청이어도 400이다. JSON으로 읽히지만 값이 틀린
  본문(예: 이름이 숫자·빈 문자열)은 비로그인이면 401, 일반 사용자면 403이다.
- 관리자 여부는 요청 시점에 저장된 역할로 판단한다. 로그인 후 역할이 관리자에서 일반 사용자로 내려가면 다음
  요청부터 403이고, 일반 사용자에서 관리자로 올라가면 다시 로그인하지 않아도 허용된다.
- 탈퇴 처리된 관리자 계정의 로그인 상태로 요청하면 비로그인과 같은 401이다(001-auth FR-011).
- 다른 출처의 `Origin`을 붙인 추가·수정·삭제 요청은 관리자여도 403이다(001-auth FR-013, 출처 검사가 가장 먼저).
- 목록 조회는 상태를 바꾸지 않으므로 다른 출처의 `Origin`이 붙어도 200이다.
- 요청 본문이 JSON이 아니거나 정의되지 않은 추가 필드가 있으면: JSON이 아니면 400, 추가 필드는 무시한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 기술 스택과 포지션 두 종류의 태그를 서로 독립된 목록으로 저장해야 한다. 각 태그는
  식별자와 이름을 가진다.
- **FR-002**: 누구나(로그인하지 않은 방문자 포함) 기술 스택 목록과 포지션 목록을 각각 조회할 수 있어야 한다.
  응답은 `{ "items": [...] }` 형태이고, `items`는 해당 종류의 태그 전체를 id와 name으로 담아 대소문자를 무시한
  이름 오름차순(그 외에는 문자 코드 순서)으로 정렬한다.
- **FR-003**: 관리자는 이름을 지정해 기술 스택 또는 포지션을 추가할 수 있어야 한다. 성공 응답은 201이며 새
  태그의 id와 name을 담는다.
- **FR-004**: 관리자는 기존 기술 스택 또는 포지션의 이름을 수정할 수 있어야 한다. 성공 응답은 200이며 수정된
  태그의 id와 name을 담는다. 식별자는 바뀌지 않는다.
- **FR-005**: 이름은 문자열이어야 하고, 앞뒤 공백 제거 후 1자 이상 30자 이하(문자 수 기준)여야 하며 줄바꿈·탭 등
  제어문자를 포함할 수 없다. 그 밖의 문자(특수문자·한글·사이 공백)는 허용한다. 공백 제거 후 값을 저장한다.
  위반 시 400이다.
- **FR-006**: 같은 종류 안에서 이름은 고유해야 한다(공백 제거 후, 대소문자 무시). 추가·수정으로 중복 이름이
  생기면 409이며 저장된 데이터는 바뀌지 않는다. 동시 요청에서도 고유성이 지켜지고 5xx를 내지 않는다.
- **FR-007**: 관리자는 기술 스택 또는 포지션을 삭제할 수 있어야 한다. 성공 응답은 본문 없는 204이며, 삭제된
  태그는 저장소에서 완전히 제거되어 이후 조회에 나오지 않고 같은 이름을 다시 추가할 수 있다. 사용자·공고와의
  연결이 있어도 삭제는 거부되지 않으며 그 태그를 가리키는 연결도 함께 삭제된다(연결 기능이 지켜야 할 계약).
- **FR-008**: 수정·삭제 대상 id의 태그가 없으면 404, id 형식이 올바르지 않으면 400이다.
- **FR-009**: 시스템은 다른 기능이 재사용할 수 있는 "관리자 전용" 보호 수단을 제공해야 한다. 비로그인 요청은
  001-auth의 로그인 필수 보호와 같은 401, 로그인했지만 요청 시점에 저장된 역할이 관리자가 아니면 403으로 거부한다.
  이 보호 수단은 입력 값 검증보다 먼저 적용된다. 단, 앱 공통 본문 JSON 파싱(깨진 JSON → 400)은 이 보호 수단보다
  먼저다.
- **FR-010**: 태그 추가(FR-003)·수정(FR-004)·삭제(FR-007)는 모두 관리자 전용 보호 수단(FR-009)을 적용한다.
  목록 조회(FR-002)는 적용하지 않는다.

### Key Entities *(include if feature involves data)*

- **TechStack(기술 스택)**: 사용자가 다룰 줄 알거나 공고가 요구하는 기술. 속성: 식별자(UUID), 이름(공백 제거 후
  1~30자, 기술 스택 사이에서 대소문자 무시 고유). 이후 사용자 기능과 공고 기능이 각자의 연결로 이 태그를 참조하며,
  태그가 삭제되면 그 연결도 함께 삭제된다.
- **Position(포지션)**: 사용자가 맡을 수 있거나 공고가 모집하는 역할(예: 백엔드, 프론트엔드). 속성: 식별자(UUID),
  이름(공백 제거 후 1~30자, 포지션 사이에서 대소문자 무시 고유). 기술 스택과 같은 방식으로 참조·삭제된다.
- **User(사용자)**: 001-auth에서 정의. 이 기능은 역할(USER/ADMIN)만 읽어 관리자 여부를 판단하며 사용자 데이터를
  바꾸지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 추가·조회·수정·삭제 각각의 수용 시나리오 전부가 기술 스택과 포지션 두 종류 모두에 대해 자동
  테스트로 통과한다.
- **SC-002**: 일반 사용자 또는 비로그인 방문자가 태그를 추가·수정·삭제할 수 있는 경로가 0개다(테스트로 확인).
- **SC-003**: 잘못된 입력(형식 오류·중복 이름·없는 id)은 모두 4xx로 응답하고 5xx가 발생하지 않는다.
- **SC-004**: 사용자·공고 기능 담당자가 이 기능 머지 후 태그 관련 파일을 수정하지 않고 기술 스택·포지션을
  참조하는 연결을 만들 수 있다. 다른 기능은 관리자 전용 보호 수단을 수정 없이 가져다 쓸 수 있다.

## Assumptions

- 사용자↔기술 스택/포지션, 공고↔기술 스택/포지션 연결은 범위 밖이다. 사용자·공고 기능이 각자 만들되, 태그가
  삭제되면 연결도 함께 삭제되도록 만들어야 한다(FR-007).
- "대소문자 무시 고유"는 이름을 소문자로 바꾼 값에 거는 고유 제약으로 구현한다. 스키마 도구가 이를 직접 표현하지
  못하면 마이그레이션 SQL을 적용 전에 손봐야 한다.
- 태그 식별자는 사용자와 같은 UUID 문자열이다.
- 태그 단건 조회, 검색·필터·페이지 나누기, 정렬 옵션, 태그 설명·아이콘·색 같은 추가 속성, 여러 개 한 번에
  추가·삭제는 범위 밖이다. 태그 수는 수백 개 이하로 보고 목록은 한 번에 전부 반환한다.
- 삭제는 하드 딜리트다(사용자와 달리 삭제 시각을 남기지 않는다).
- 기본 태그 목록을 미리 채우는 시드 데이터는 범위 밖이다. 관리자가 API로 등록한다.
- 관리자 지정은 001-auth대로 운영자가 저장소에서 역할 값을 직접 바꾼다. 테스트는 사용자를 만든 뒤 역할을
  저장소에서 관리자로 바꿔 준비한다.
- 관리자 전용 보호 수단은 기존 로그인 필수 보호 수단과 같은 공유 위치에 둔다(팀장 브랜치 작업이라 승인 불필요).
- 성능 목표는 범위 밖이다.
